# 项目背景与排查经过

本文记录项目形成的原因、证据和取舍。案例已脱敏，不包含真实设备地址、账号、代理配置或访问日志原件。`chat.example.com` 等名称仅为示例。

## 从 VPS 流量告警开始

一台按月限额的 VPS 收到流量即将用尽的告警，但使用者感觉日常用量没有明显变化。VPS 运行网络代理，仅看服务商总量或网卡计数，无法回答“流量到底去了哪里”。

需求逐渐明确为：

1. 优先统计目标域名/IP 的流量 Top 排行，上下行分开。
2. 可用时统计来源 IP；不为审计给每个设备分配单独 UUID。
3. 保留至少一个月，存储不能无限增长。
4. 不保存聊天正文、完整 URL 或原始数据包。
5. 能解释误差，不把推断写成确定事实。

透明代理、出口 NAT 和共享凭证限制来源归因，共享 CDN IP 又限制域名归因。这决定了仅在 VPS 上按 IP 统计还不够。

## 服务器侧可以证明什么

服务器端可以分别观察网卡、客户端到代理、代理到外站的流量，判断流量是否回升、主要目标 IP 和来源 IP 是哪些。

但一份代理下载经过“外站到 VPS”和“VPS 到客户端”两段路径。网卡收发相加，不一定等于应用下载量，也不一定等于服务商计费口径。

Cloudflare 等 CDN 的 IP 被多个域名共享。某域名现在解析到某 IP，不能证明该 IP 过去的全部流量都属于它。服务器侧排行只能提供线索。

## 加入本地代理的域名证据

HTTP CONNECT、SOCKS 等代理连接元数据能提供目标域名。本地域名统计与 VPS IP 排行结合，可以缩小范围，但两端覆盖范围、协议开销和时间窗口不同，字节数不会天然一一相等。

当前 DNS 解析只能验证当前映射，不能替代历史 DNS 记录。

## 一次后台重试循环的排查

排查发现某台电脑持续建立大小相近的短连接：上传很少，每次下载约数十 KiB。频率足够高时，即使每次响应很小，全天也能累计到 GiB 量级。

| 证据 | 能证明 | 不能单独证明 |
| --- | --- | --- |
| 操作系统连接表中的 PID、源端口 | 哪个进程发起连接 | HTTPS 具体接口及内容 |
| 代理日志中同一源端口和时间 | 该连接请求的域名 | 应用内部为什么请求 |
| 客户端执行器退出和固定间隔重试日志 | 存在失败重启循环 | 所有异常字节都由此造成 |
| 退出应用后连接消失、计数停止增长 | 这些连接与该应用相关 | 应用内部各功能的精确占比 |
| 新版重开后成功连接、流量收敛 | 当前没有复现相同循环 | 特定上游补丁已永久修复问题 |

当时观察到桌面程序选择的服务域名，与内置命令行组件接受的目标域名范围不一致。子进程退出后，父进程以很短的固定间隔再次启动；启动前又查询元数据或注册执行器，形成持续后台活动。

证据支持一个兼容性与重试逻辑问题，但没有逐个 HTTPS 请求的字节记录，不能将全部异常下载精确归因给某个接口。本项目不声称这是官方确认的缺陷，也不提供该客户端的修复补丁。

## 系统代理不等于应用实际路径

排查还遇到“系统代理指向本机，但进程却连接另一台代理机器”的情况。最终找到应用单独加载的 `.env` 代理设置。

系统设置、shell 环境、应用配置和已经运行的进程，可能使用不同路径。判断时应先看真实连接，再追溯配置来源，不能只根据桌面代理开关下结论。

切换路径需要闭环验证：备份配置，修改明确的代理项，正常重启需要重新加载配置的应用，再确认连接进入预期代理。本项目安装器不会自动修改这些应用设置。

## 为什么选择 Mihomo API

Clash Verge 的内核已经维护域名、连接字节计数、代理链和命中规则。现有 Unix API 能提供这些信息，桌面概览之外所缺少的是“持续保存历史聚合”。

选择时比较过两条路线：

- **API 快照**：实现简单、资源较低，可直接利用域名和节点信息；短连接细分可能遗漏。
- **本地数据包计数并关联元数据**：观察更细，但跨接口去重、协议解析、进程映射和系统权限都更复杂。

首版选择 API，并明确展示未归属差额与覆盖率。目标是识别主要流量成分，不是声称每个字节都已精确归因。
