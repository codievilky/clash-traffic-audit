# 验证与资源测量

```sh
python3 -m unittest discover -v
python3 test_clash_audit.py --capacity
python3 install.py install --dry-run
node --check app.js
node test_ui.js
```

测试使用合成连接和临时数据库，不依赖真实访问记录。安装器测试 mock `launchctl`，不会安装或停止真实服务。

## 主要测试边界

首次基线、已有/新建/迟到连接、关闭连接的未归属流量、采集器恢复、内核重启、采样间隙、日界线、保留期限、细分上限、排行截断分母、只读 HTTP/CSV、启动项生成与安装回退，以及页面异步请求乱序。

## 最大基数容量

构造 35 天每天达到细分上限的数据、各路径溢出项、8,192 个活动基线、较长字段和较大计数，再开启一次全表更新事务观察回滚日志。

初始验证结果：

| 项目 | 数值 |
| --- | ---: |
| 每日聚合行数 | 77,420 |
| 数据库 | 26,411,008 字节 |
| 全表更新回滚日志 | 25,523,288 字节 |
| 数据库配置上限 | 50,331,648 字节 |
| 数据库双份加日志预留预算 | 103,809,024 字节 |
| 目标预算 | 134,217,728 字节 |

这是对既定限制的验证，不代表无限域名都能逐条保留。超过细分上限会归入“其他”。这些限制与字段长度、响应体、日志和活动基线上限共同约束资源。

## CPU 与内存样本

两台 macOS 电脑每秒读取并聚合一个快照，共采样 20 次，当时约 30—70 条活动连接：

- 采集进程平均约占单核 CPU 的 0.2%；
- 短时探测进程峰值内存约 14—20 MiB；
- 带 SQLite 和网页服务的完整守护进程，一次实际观察约 24 MiB RSS。

这些是特定负载下的样本，不是占用承诺。内核处理接口的额外 CPU、浏览器、较大查询和更高连接数需要分别测量。

## 精度边界

低活动量试采中，差额曾低于 1%；应用启动产生大量短连接时，差额会增大。因此不宣传固定精度，而是显示实际覆盖率，保留独立的总量与细分数据。

## 部署验收

1. Unix 控制接口可用，版本和连接结构符合预期。
2. 页面、JSON、CSV 和筛选结果一致。
3. 正常重启后累计保留，SQLite `quick_check` 返回 `ok`。
4. 只监听本机地址，进程以预期用户运行。
5. 若切换应用代理，实际连接已进入本机 Clash。

测试通过不代表已经运行满 35 天；长期保留依赖容量限制、清理逻辑、主机与文件系统正常工作。
